# Release management

## Purpose

Holqa records version intent from day one but publishes nothing yet. This skill explains how to add changesets correctly, choose the bump, write commit messages, and recognize what must happen before any package goes public. **Agents never publish.**

## When to use

- A change touches a package's runtime behavior, exports, types, diagnostic codes, CLI flags, exit codes, or output formats.
- Writing a commit message or PR description.
- Someone asks to publish, tag, version, or remove `"private": true`.

## Current state

| Item | State |
| --- | --- |
| Packages | All `"private": true`, version `0.0.0` |
| Changesets | Configured in `.changeset/config.json` (`baseBranch: main`, `privatePackages: { version: false, tag: false }`, `commit: false`) |
| Publishing | Not automated, not configured. No release workflow exists |
| CI | `.github/workflows/ci.yml` runs `pnpm install --frozen-lockfile` and `pnpm check` |
| Root `CHANGELOG.md` | Exists; package changelogs will be generated by Changesets once versioning is enabled |

Because private packages are skipped, changesets have no versioning effect today. Add them anyway for public-contract changes: they record intent for the first release.

## Instructions

### 1. Decide whether a changeset is needed

| Change | Changeset? |
| --- | --- |
| Behavior, exports, types, diagnostic codes, CLI behavior of a package | Yes |
| Docs, tests, CI, internal tooling, `.agents/`, scripts only | No |
| Refactor with no observable change | No (say so in the PR) |

### 2. Create it

```bash
pnpm changeset
```

Select packages, choose the bump, and write a user-facing summary (what changed, what to do). Commit the generated `.changeset/*.md` with the change. A changeset file looks like:

```markdown
---
"@holqa/core": minor
---

Add `isResourceId`, a type guard that mirrors `parseResourceId` without allocating a diagnostic.
```

### 3. Choose the bump (SemVer)

| Change | Before 1.0 (`0.y.z`) | From 1.0 |
| --- | --- | --- |
| Breaking change to exports, types, behavior, CLI output or exit codes, manifest format | minor | major |
| Backward-compatible feature | minor or patch | minor |
| Bug fix with no API change | patch | patch |

Diagnostic codes are stable at every version: add only; never rename, remove, or reuse. Changing the resource ID grammar is breaking once anything is published.

### 4. Commit messages (Conventional Commits)

```text
feat(core): add isResourceId type guard
fix(compiler): include the JSON path in serialization diagnostics
docs(adr): add 0012 manifest versioning
chore(deps): update tsdown to 0.23.2
feat(cli)!: change --json error output shape

BREAKING CHANGE: errors are now written as {"diagnostics":[...]} on stderr.
```

Scope is a package directory (`core`, `compiler`, `cli`) or an area (`adr`, `agents`, `deps`). Commit messages describe history; changesets decide versions. Only commit when the user asks.

### 5. Changelog entries

- Written for package users, not maintainers: behavior and migration, not file names.
- Breaking entries lead with the break and the migration step.
- Never claim features that do not work; changelogs follow the same honesty rules as docs.

### 6. Publishing readiness (do not perform)

Removing `"private": true` is a separate, explicitly approved maintainer decision. The full checklist lives in [docs/contributing/releasing.md](../../../docs/contributing/releasing.md); in short:

- A meaningful, non-stub API with docs, reference pages, and JSDoc.
- Listed in `examples/package-smoke`; `exports`, `types`, `files`, `sideEffects`, `engines` verified; no `@/` leaks.
- Packaging lint considered (publint, Are the Types Wrong); not yet part of `pnpm check`.
- Complete metadata; Apache-2.0 confirmed by the repository owner (never claim legal review).
- `@holqa` npm organization controlled by maintainers with 2FA; integration package names decided.
- Publishing from CI with provenance via a reviewed release workflow; no publishing from developer machines.
- Maintainer approval in the PR.

Agents must not run `pnpm publish`, `changeset publish`, `npm publish`, `changeset version` (unless asked to preview locally and revert), create git tags or GitHub releases, or edit `access`/`privatePackages` in `.changeset/config.json` without explicit maintainer instruction.

## Verification checklist

- [ ] A changeset exists for every public-contract change (or the PR states why none is needed).
- [ ] Bump type follows the pre-1.0 / post-1.0 table; breaking changes include a migration note.
- [ ] Commit messages follow Conventional Commits, with `!` and `BREAKING CHANGE:` for breaks.
- [ ] No package was un-privated, versioned, tagged, or published.
- [ ] Docs (`docs/reference/*`, status model) match the change.
- [ ] `pnpm check` passes and the real result is reported.
