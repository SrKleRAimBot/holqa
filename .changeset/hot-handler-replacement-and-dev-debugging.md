Replace handler implementations in place during development, add a local development dashboard, and record and replay invocations in tests.

- `@holqa/runtime-bun`: a versioned handler registry. `runtime.replaceHandlers(registrations, { sources })` installs new implementations of registered handlers atomically as one registry version; invocations are pinned to the implementation current when they get their concurrency slot, so in-flight work finishes on the code it started with. Replaced versions retire when their last execution finishes. `runtime.handlerVersions()` and `stats().versions` (`HandlerVersionInfo`, `HandlerRegistryStats`, `HandlerReplacement`, `ReplaceHandlersOptions`) describe them. Invocations of replaced implementations log `handlerVersion` and set `holqa.handler.version` on their span; applications that never replace handlers log exactly what they did before. Behaviour change: each handler (and each later version of it) now receives its own view of the application scope, so `context.scope` and `context.scope.signal` are different objects for different handlers even when nothing is replaced; values are still shared, but the view's `signal` also aborts when that version retires, and scoped values that only retired versions used are disposed of at retirement. `Runtime` gains the required members `replaceHandlers` and `handlerVersions`, and `RuntimeStats` the required field `versions`, so hand-built objects of those types no longer type-check (a major change after 1.0).
- `@holqa/cli`: `holqa dev` applies changes that only touch handler code (the manifest and entry point map are unchanged, and no changed file is imported by the application module) by rebundling the affected handler modules and replacing their handlers in the running generation, without recreating local state or consumers. Modules that create timers, listeners, servers or globals while loading, modules with the comment `holqa:restart-on-change`, dependency and compiler configuration files, and every other change restart the generation process as before; the `build` event's new `reload` field says which and why. New events `handlers.swapped`, `handlers.swap-failed` and `handlers.swap-refused`; failure events gain `stale`. New flags `--no-hot` (restart on every change) and `--no-dashboard`. A read-only dashboard is served at `/_holqa/dashboard` on loopback addresses. When a queue's contract changes, messages already waiting in it are checked against the new contract and reported. Behaviour change for `holqa dev --json` consumers: a `build` event is no longer always followed by `generation.ready` or `generation.failed`; when `build.reload.strategy` is `"swap"` it is followed by `handlers.swapped`, `handlers.swap-failed`, or `handlers.swap-refused` and a second `build` for the restart. Consumers should check `reload.strategy` (or pass `--no-hot`) and ignore unknown event types and fields.
- `@holqa/core`: new diagnostic codes `HOLQA_HANDLER_REPLACEMENT_INVALID` and `HOLQA_QUEUED_MESSAGE_INCOMPATIBLE`; `ApplicationScope` documents per-version scope views.
- `@holqa/testing`: `TestApp.recording()` returns what every handler received as a sanitized `holqa.recording/1` document, `TestApp.replay()` runs recorded invocations again deterministically, and `TestApp.chain(rootId)` lists a root operation's invocations in causal order with their recorded inputs. New exports `Recording`, `RecordedInvocation`, `ChainStep`, `RecordingOptions`, `ReplayOptions` and `recordingFormat`. `TestApp` gains required members, so hand-built `TestApp` objects no longer type-check (a major change after 1.0).
