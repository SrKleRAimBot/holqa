# Releasing

How changes are versioned, and what has to happen before any Holqa package is published.

> **Current state:** Every package is `"private": true`. Nothing is published to npm and no automated publishing is configured. Changesets is set up so that version intent is recorded from the start.

## Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/):

```text
<type>(<scope>): <summary>

feat(core): add isResourceId type guard
fix(compiler): include the JSON path in serialization diagnostics
docs(adr): add 0012 manifest versioning
chore(deps): update tsdown to 0.23.2
```

Common types: `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`, `ci` and `chore`. The scope is usually a package directory name (`core`, `compiler`, `cli`) or an area (`adr`, `agents`, `deps`). Mark breaking changes with `!` (`feat(core)!: ...`) and a `BREAKING CHANGE:` footer.

Commit messages describe history. Changesets, not commit messages, decide versions.

## Changesets workflow

For a change that affects the behaviour, API or types of a package:

```bash
pnpm changeset
```

1. Select the affected packages.
2. Choose the bump type (`patch`, `minor`, `major`, following the policy below).
3. Write a summary for users of the package: what changed and what they need to do. The summary becomes the changelog entry.
4. Commit the generated `.changeset/*.md` file with your change.

Changes that only touch docs, tests, CI or internal tooling do not need a changeset.

**Private packages are not versioned or published.** Changesets skips `"private": true` packages, so changesets for them have no effect today. Add one anyway when you change a package's public contract (exports, types, diagnostic codes, CLI behaviour). It records intent for the package's first release.

Versioning and publishing are not automated. When publishing is enabled, the expected flow is `changeset version` (which applies pending changesets and updates versions and changelogs) followed by a reviewed publish step. That flow will be documented when it is set up.

## Versioning policy

Packages follow [Semantic Versioning](https://semver.org/).

| Change | Before 1.0 (`0.y.z`) | From 1.0 |
| --- | --- | --- |
| Breaking change to exports, types, runtime behaviour, CLI output or exit codes, or the manifest format | minor (`0.y` → `0.y+1`) | major |
| Backwards-compatible feature | minor or patch | minor |
| Bug fix with no API change | patch | patch |

- **Pre-1.0:** APIs may change in minor releases. Breaking changes still need a changeset that states the break and the migration.
- **Diagnostic codes are a stable contract at every version.** A code is never renamed or reused for a different meaning. Codes are only added, and retired codes stay reserved.
- Changing the resource identifier grammar (currently an initial proposal, see [ADR 0004](../architecture/decisions/0004-stable-logical-resource-identities.md)) is a breaking change once any package is published.
- Internal dependencies use `workspace:*`. When publishing is set up, pnpm replaces them with real version ranges in the published manifests.

## Readiness checklist before removing `"private": true`

A package is published only when every item below is true. Removing `"private": true` is a reviewed, explicit decision. It is never a side effect of another change.

- [ ] **A meaningful API.** The package does something useful on its own. It is not a scaffold, and it does not ship stubs that pretend to work.
- [ ] **Documentation.** The package README describes what is implemented and labels everything else as planned. The [packages reference](../reference/packages.md) and any [diagnostic codes](../reference/diagnostic-codes.md) are current. Public functions have documentation comments.
- [ ] **Exports and types verified.** The package is listed in `examples/package-smoke`. `exports`, `types`, `files`, `sideEffects` and `engines` are correct. No `@/` aliases leak into `dist/`, and the `.d.ts` files resolve for a consumer.
- [ ] **Packaging lint considered.** Run [publint](https://publint.dev) and [Are the Types Wrong](https://arethetypeswrong.github.io) (`attw --pack`) against the packed tarball. These tools are not yet part of `pnpm check`. Decide whether to add them to CI when the first package is published.
- [ ] **Metadata.** `description`, `license` (Apache-2.0, which the repository owner must confirm before public release), `repository.directory`, `keywords` and `homepage` are set. A `CHANGELOG.md` is generated by Changesets.
- [ ] **npm ownership.** The `@holqa` npm organization exists and is controlled by the maintainers. Package names are confirmed, including the integration package names, which are not decided yet. Publishing accounts use 2FA.
- [ ] **Provenance.** Publishing happens from CI with npm provenance (`--provenance` / trusted publishing), not from a developer machine. Credentials are scoped tokens or OIDC, and are stored as CI secrets.
- [ ] **A release workflow.** A reviewed CI workflow (for example the Changesets GitHub Action) is in place and documented here. Until it exists, nothing is published.
- [ ] **Maintainer approval** in the pull request that removes `"private": true`.
